# ch11-2 · 쿠키 인증과 CORS가 다시 만나는 곳

> 책 [11장 5절](https://library.younggeun0.dev/react-to-spring/11#s5)

React(`localhost:3000`)가 쿠키를 실어 API(`localhost:8080`)를 부를 수 있게 했다.

```bash
git diff ch11-1 ch11-2 -- . ':!steps'
```

- `CorsConfig`: 원서대로 `setAllowCredentials(true)`. 쿠키 같은 인증 정보를 실은 교차 출처 요청을 허용한다. 5장에서 "일부러 비워 둔 설정"이 이것이다
- `SessionSecurityConfig`: `.cors(Customizer.withDefaults())`. 「앱 보충」 [11장 5절의 원문 보정 상자](https://library.younggeun0.dev/react-to-spring/11#s5)는 이 줄을 "명시해 두는 편이 안전하다"고 한다. 사실 `CorsConfigurationSource` 빈이 있으면 Spring Security 6은 이 줄 없이도 필터체인 안에서 CORS를 처리한다(9장 TRACE의 `CorsFilter (5/13)`). 그래서 이 줄은 동작을 바꾸지 않고, 설정을 읽는 사람에게 "CORS는 Security가 처리한다"를 드러내는 역할이다
- `CorsConfig`의 `CorsFilter` 빈(5장)을 지웠다. 9장부터 Security가 이미 CORS를 처리하고 있어서, 남겨 두면 같은 일을 두 번 한다

이 단계에서 동작을 바꾼 것은 `setAllowCredentials(true)` 하나다.

## 실행해 보기: 브라우저

```bash
./gradlew bootRun
```

1. 브라우저로 `http://localhost:8080/api/tasks`를 열고 `ara` / `pass1234`로 로그인한다. (`/login`을 직접 열어 로그인하면 `/`로 가는데, 이 앱에는 루트 페이지가 없어서 404 오류 페이지가 나온다. 정상이다.)
2. 같은 브라우저에서 `http://localhost:3000`의 페이지를 연다. React 개발 서버가 없다면 빈 폴더에서 `npx serve -l 3000`.
3. 그 페이지의 개발자 도구 콘솔에서 두 요청을 비교한다.

```js
// 쿠키를 함께 싣는다
const a = await fetch('http://localhost:8080/api/tasks', { credentials: 'include' })
a.status, await a.json()          // 200, 할 일 목록

// 쿠키를 싣지 않는다 (fetch 기본값)
const b = await fetch('http://localhost:8080/api/tasks')
b.redirected, b.url               // true, 'http://localhost:8080/login'
```

Network 탭에서 두 요청의 Request Headers를 비교한다. 첫 요청에만 `Cookie: JSESSIONID=…`가 있다. 둘째는 로그인하지 않은 요청으로 취급돼 로그인 폼으로 리다이렉트됐다.
콘솔에서 `document.cookie`를 쳐 봐도 `JSESSIONID`는 안 보인다. HttpOnly라 자바스크립트로 읽을 수 없고, 브라우저만 실어 보낸다.

## 실행해 보기: curl

```bash
curl -i -X OPTIONS http://localhost:8080/api/tasks \
  -H "Origin: http://localhost:3000" \
  -H "Access-Control-Request-Method: GET"
```

```
HTTP/1.1 200
Access-Control-Allow-Origin: http://localhost:3000
Access-Control-Allow-Methods: GET,POST,PUT,DELETE,OPTIONS
Access-Control-Allow-Credentials: true
```

`Access-Control-Allow-Credentials: true`가 새로 붙었다. ch11-1에서는 이 헤더가 없어서, 브라우저가 쿠키를 실은 요청의 응답을 자바스크립트에 넘겨주지 않는다.

## 직접 깨뜨려 보기: `*`와 `allowCredentials(true)`

`CorsConfig`의 허용 출처를 `List.of("*")`로 바꾸고 띄운 뒤, `Origin`을 실어 요청한다.

```bash
curl -i http://localhost:8080/api/users/summary -H "Origin: http://localhost:3000"   # 500
curl -i http://localhost:8080/api/users/summary                                       # 200
```

서버 로그:

```
java.lang.IllegalArgumentException: When allowCredentials is true, allowedOrigins cannot contain the special value "*" since that cannot be set on the "Access-Control-Allow-Origin" response header. To allow credentials to a set of origins, list them explicitly or consider using "allowedOriginPatterns" instead.
```

브라우저 콘솔보다 서버가 먼저 거부한다. `Origin`이 없는 요청은 CORS 처리를 거치지 않으니 멀쩡하다. "아무 출처에서나 쿠키 인증"은 허락할 수 없다는 뜻이다. 확인했으면 `git checkout -- .`으로 되돌린다.

## CSRF는 켜져 있다

이 설정은 10장과 달리 CSRF를 끄지 않았다. React에서 쿠키 인증으로 `POST`·`PUT`·`DELETE`를 보내면, CSRF 토큰을 함께 보내기 전까지 403이다([11장 4절의 원문 보정 상자](https://library.younggeun0.dev/react-to-spring/11#s4)). 막는 게 정상이고, 끄지 말고 Spring Security 레퍼런스 CSRF 장의 SPA 절을 따라 구성한다.
